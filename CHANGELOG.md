# Changelog / milestones

All dates 2026. Kernel reference build is **`7.1.0-next-20260626`** unless noted.

## Kernel reference

- **`7.1.0-next-20260626`** — linux-next, compiled 2026-06-26 18:28 (CEST), gcc 13.3.0, GNU ld 2.42. This is *the* reference build carrying `x1p42100` support.
- The stock Arch `linux-aarch64` package (7.1.x) is held in `IgnorePkg`: GRUB boots the custom `/boot/Image`, not the stock kernel/initramfs. A tool reporting "a newer kernel available" is looking at the stock package, not the running kernel.

## Milestones

- **2026-06-26** — First successful boot to root shell on the custom linux-next kernel; console + Bluetooth working.
- **2026-06-28** — KDE desktop shown on the internal panel; Wi-Fi associated, SSH reachable. (Early USB-boot media proved unreliable — a marginal USB flash controller caused ext4 I/O corruption under repeated reboots.)
- **2026-06-30** — Storage-strategy iterations (USB key → Ventoy vdisk → USB SSD); GPT-repair workflow for raw-writing a small image onto a large disk; WPA3-SAE Wi-Fi fix.
- **~2026-07 (early)** — Moved to an **internal ext4 install**, dual-boot with Windows, for full reliability. Internal display + KDE + GPU accel working.
- **2026-07-03** — HW video codec fixed (supplied `qcvss8380_pa.mbn`); `/dev/video0` + `/dev/video1` live. Audio confirmed working (topology now in linux-firmware). Battery telemetry identified as the main remaining issue.
- **2026-08-06** — **Boot 1.5 s shorter, and audio ready 3 s earlier.** `audioreach_send_cmd_sync()` gives every command a 5 s budget. `APM_CMD_GET_SPF_STATE` does not need it: it is the readiness probe `q6prm` issues before populating its children, its caller already treats failure as `-EPROBE_DEFER` and retries, and on the attach path the first probe always misses while the second always succeeds — one timeout per boot, five seconds spent waiting for a reply that never comes. Since the sound card only registers once the probe gives up, anything polling `/proc/asound/cards` blocked for the whole timeout; `sp12-audio-ucm.service` was the slowest unit of the boot at 4.4 s. `patches/0009` gives that one probe 1 s and lets the retry work: the service drops to **0.37 s**, the card appears at 5.74 s instead of 8.71 s, total boot 8.21 s → 6.74 s. Every other command keeps `5 * HZ`. The error line itself remains — the race is unchanged, only the wait is shorter. Separately, **battery**: telemetry turns out to be complete (93 % health, 34.88 of 37.45 Wh design) and charge limiting is both functional and persisted in the PMIC's SDAM, so it is visible to Windows too — worth knowing before setting it. Measured autonomy levers, A-B-A: 90 → 60 Hz is worth **0.9 W** (6.5 h → 7.7 h); dropping `clk_ignore_unused` / `pd_ignore_unused` is worth 0.10 W, i.e. nothing measurable, so they stay. At 4.5 W idle the session dominates the kernel — a running Electron app costs more than every tunable examined here.
- **2026-08-06** — **Kernel rebuilt from our own tree: nftables, policy routing — and a load-bearing module nobody knew about.** `CONFIG_LOCALVERSION="-nft"` gives the new kernel its own `/lib/modules`, so both coexist and a separate GRUB entry points at each; nothing existing was overwritten. `iptables v1.8.13 (nf_tables)` and `ip rule` now work, the `iptables-legacy` PATH shim is gone, and Tailscale finally wires its `ts-*` chains — 4 rules against 0, because without `IP_MULTIPLE_TABLES` it created the chains but never referenced them. Two traps found by rebuilding, both invisible until then. First, `make Image modules dtbs` produces **nothing**: `patches/serie-complete/0016` references `QCOM_SCM_VMID_SELF_OWNER`, a constant no patch in the series defines, and `dtbs` dies before `Image` is written — build without `dtbs`, this port uses a vendor-derived DTB anyway. Second, and worse: `/lib/modules/<version>/updates/` — which takes precedence over `kernel/` — held a hand-placed `uhid.ko` from the lost WSL build, while `CONFIG_UHID` is set in no configuration at all. The Bluetooth mouse had been working on that file alone; on a kernel faithful to its config it pairs and then sends nothing, which reads like a Bluetooth fault rather than a missing module. Inventory `updates/` before any rebuild. Also of note: the `updates/` copy of `surface_aggregator_registry` carried a hand-trimmed `sp12in` group while the tree carries the upstream one — both work here, the tablet-mode switch simply appears as `POS Tablet Mode Switch` instead of `KIP`.
- **2026-08-05** — **Hardware clock working at EL2, and the reason EL2 costs the EFI variables.** The mechanism was measured, not assumed: after Secure Launch TrustZone still answers a version query (`TZ_OWNER_SIP` / `INFO_VERSION` → `0x1402000`) but refuses the trustlet manager (`TZ_OWNER_QSEE_OS` / `APP_LOOKUP` → `-22`). So `qcom_qseecom_uefisecapp` never probes, `efivars` never registers — 0 variables at EL2 against 110 at EL1 on the same kernel — and `qcomtee` reports `QTEE version 0.0.0` instead of `5.2.0`. Mainline cannot reload a trustlet, so this is a dead end rather than an unexplored lead. A separate experiment settled a competing hypothesis: restoring a *restricted* cache sweep over `EfiRuntimeServices{Code,Data}` in `sl_ExitBootServices()` boots fine but does **not** bring the variables back, so removing the sweep was never the cause. Knock-on effect on the clock: `pm8xxx_rtc_probe_offset()` reads its epoch offset from the UEFI variable `RTCInfo` and returns `-EPROBE_DEFER` with no give-up path while `CONFIG_EFI=y`, so the RTC never registered at all. Fixed with `qcom,rtc-offset`, a third source tried after nvmem and before UEFI (`patches/0008`); the clock is now set at 3.0 s of uptime, sixty seconds before NTP. The nvmem route used by `sc8280xp-crd`/`-arcata`/`-blackrock` (cell `rtc_offset@bc`) is not transposable: on the pmk8550 a SDAM's usable window is `0x40..0x7f`, so `0xbc` is not addressable, and SDAM 6 is densely written by firmware — not somewhere to gamble on a dual-boot machine. Two traps on the way: `hwclock --show --utc` prints **local** time with its offset (`--utc` describes the RTC, not the output), and `scripts/setlocalversion` no longer honours `.scmversion`, so a module built from a git tree gets a `+` in its `vermagic` and silently refuses to load without `MODVERSIONS` — build with `KERNELRELEASE=` set explicitly.
- **2026-08-03** — **First patch accepted upstream.** `drm/panel-edp: Add Sharp LQ120P1JX51 (Surface Pro 12in 1st Ed.)`, commit `6ed8d820cea9cae226f500d3af86e156eede27f6` in `drm-misc-next`, `Reviewed-by: Douglas Anderson`. The v1 claimed the EDID was not obtainable — Doug pushed back, and he was right: the DRM connector does not export it and `CONFIG_DRM_DP_AUX_CHARDEV` is gone, but the AUX bus registers as an i2c adapter, so `i2ctransfer -y <bus> w1@0x50 0x00 r128` reads it. (`i2cdump` in byte mode does not: it drops a header byte and yields a bad checksum while still looking plausible.) The EDID carried a Display Product Name, so the entry names the real panel instead of "Unknown". Every SP12 with this Sharp panel now loses the deliberate `WARN_ON` and gets `unprepare = 500 ms` instead of 2000.
- **2026-07-31** — **SAM registry trimmed to what actually exists.** Two HID devices probed and failed every boot with `-EPROTO` (`01:15:02:02:00` pen stash, `01:15:01:06:00` sensor collection); a manual rebind on a fully idle system failed identically, proving absence rather than a boot-time race. Two traps on the way: the file also contains an `ssam_node_group_sp12` bound to compatible `microsoft,sp12`, which this machine never advertises (it says `microsoft,surface-pro-12in`) — dead code, and precisely the group one edits by mistake; and the installed module turned out to come from a foreign build (GCC 13.3, Ubuntu, `/root/linux-next`) whose `sp12in` group did not match the same-named group in linux-next, so reading our tree to reason about it was misleading. The live device list settled it. Console noise cut further with `loglevel=3` on the daily entry — 49 lines to 7, with the 42 hidden warnings each identified as benign and still captured by `dmesg`, the journal and `sp12-bootreport`.
- **2026-07-31** — **Boot cleanup pass.** `sp12-typecover` now waits on real conditions (SAM controller bound, then `surface_aggregator` bus populated) instead of two blind `sleep 1`, with a 3 s guard — longer than the old sleep, so an anomaly waits more, never less. `sp12-usbwifi` shipped disabled (internal Wi-Fi works). `sp12-bootreport` converted from an enabled service to a timer, so its deliberate 20 s settle delay no longer inflates the reported startup time. eDP panel (Sharp SHP 0x15a7) added to `edp_panels[]` to retire the deliberate `WARN_ON` splat and its register dump — note that the module also lives in the initramfs, which is the copy actually loaded, so installing it under `/lib/modules` alone changes nothing (see `patches/README.md`). Empty `modules-load.d/cdrecord.conf` override stops the failing request for the unbuilt `sg` module. Also enabled `CONFIG_BT_RFCOMM=m` — not cosmetic: without it `bluetoothd` cannot start its Hands-Free servers, so Bluetooth headsets with a microphone could not work at all.
- **2026-07-31** — **Audio working at EL2.** ADSP and CDSP are started by qebspil from UEFI before `ExitBootServices`, then *attached* by the kernel instead of started: `qcom,broken-reset` on both remoteproc nodes selects `qcom_pas_ops_no_reset` (no `.start`/`.load`), so the PAS SMC that returns `-22` is never called, and the already-running state is detected by reading the SMP2P IRQ *levels* — the DSPs signalled their boot long before Linux existed, so waiting for an edge could never work. 14 out-of-tree patches; see `patches/audio-el2-serie.md`, including the module-ABI hazard the series introduces.
- **2026-07-30** — **Internal Wi-Fi fixed at EL2.** No MSI was ever delivered — every `ITS-PCI-MSI` counter stayed at zero, PCIe root-port PME included. The cause was in our own DTS: the PCIe SMMUv3 (`iommu@15400000`) was left at `status = "reserved"`. Setting it to `"okay"` fixes it. The SMMU had been "ruled out" days earlier by a test with `arm-smmu.force_stage=1` — a parameter belonging to the SMMUv1/v2 driver, which never touches the SMMUv3. A false negative that cost days.
- **2026-07-14** — Re-established the HW-codec firmware after a restore had dropped it; a hot module reload (`modprobe -r qcom_iris && modprobe qcom_iris`) brings `/dev/video0` + `/dev/video1` back with no reboot. Documented a **safe full `pacman -Syu`** on this device: pin the entire Mesa/Vulkan userspace to a single version (`mesa`, `vulkan-freedreno`, `vulkan-mesa-implicit-layers`) so a partial upgrade can't skew the Adreno/turnip stack, with kernel + systemd held in `IgnorePkg`; cold boot validated. Added an `fstab` recipe to auto-mount the shared data partition with `nofail` + `x-systemd.automount` (see README → Stability notes).

## Upcoming

- **The SP12 DTS is now upstream.** `x1p42100-microsoft-sp12.dts` is in linux-next, and the Makefile builds both it and `x1p42100-microsoft-sp12-el2.dtb` (with the `x1-el2.dtbo` overlay). Harrison van der Byl confirms all of his patches were merged, with a compatible rename from `microsoft,surface-pro-12in` to `microsoft,sp12` to avoid a clash with the 2026 model.
- **Switching to the upstream DTS.** A node-by-node comparison found the upstream EL2 DTB already carries three of our five deltas (PCIe SMMUv3 `okay`, zap-shader and iris disabled). Volume buttons, the USB-C SBU muxes and the panel-enable regulator are absent upstream and still need carrying over.

  > **Correction (2026-08-06). The "touchscreen hardware variant" reported here did not exist, and the error was ours.** This entry previously claimed that upstream describes the touchscreen on GPIO 51/52 while this unit uses 38/48, concluded it was a board variant, and treated it as a blocker. All of that was wrong.
  >
  > `x1p42100-microsoft-sp12.dts` **does not exist in pristine `next-20260626`** — it was created in our tree by `patches/0005`, which is Harrison van der Byl's **v1**. The GPIO 51 in it is an early mistake of his, copied from similar devices, and fixed from v2 onward; [v4](https://lore.kernel.org/all/20260609145906.40854-2-harrison.vanderbyl@gmail.com/) is expected in 7.3 and describes 38/48 — this machine's actual wiring. So "upstream says 51" was us reading a patch we had applied ourselves and calling it upstream. A single `git log` on the file would have shown it.
  >
  > Two further claims were also wrong: booting with GPIO 51 leaves the touchscreen **degraded with missing pen events, not dead**; and "both descriptions are internally consistent, so it is not a typo" proved nothing — a mistake copied consistently into both the interrupt property and the pinctrl state is still a mistake.
  >
  > **There is no variant and no blocker.** Reported in error to the DT maintainers on 2026-08-04 and corrected on the thread.
