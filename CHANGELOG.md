# Changelog / milestones

All dates 2026. Kernel reference build is **`7.1.0-next-20260626`** unless noted.

## Kernel reference

- **`7.1.0-next-20260626`** — linux-next, compiled 2026-06-26 18:28 (CEST), gcc 13.3.0, GNU ld 2.42. This is *the* reference build carrying `x1p42100` support.
- The stock Arch `linux-aarch64` package (7.1.x) is held in `IgnorePkg`: GRUB boots the custom `/boot/Image`, not the stock kernel/initramfs. A tool reporting "a newer kernel available" is looking at the stock package, not the running kernel.

## Machine state

- **Mono-boot since some point after the July entries below.** The single UFS disk holds only Linux — ESP, `/home`, `/data`, root, all ext4 or vfat, **no NTFS partition anywhere**. Windows boot binaries (`bootmgfw.efi`, `bootmgr.efi`) still sit on the ESP with nothing left to boot. Entries dated July that mention dual-boot were accurate when written and are kept as history; do not read them as the current layout.

- **2026-09-03** — **The witness paid for itself: one of the three recent cuts was just a flat battery — and finding that exposed a real defect.** Its verdict agrees with the journal on all ten boots it covers, which validates the tool. `25d5614b` is textbook and **not an anomaly**: unplugged 1 September 09:39 (`usb` 1→0) at 33.74 Wh, then a smooth monotonic decline over **19 hours** — 0.69 Wh at 04:11, 0.00 Wh at 04:32, dead at 04:33 — with voltage tracking it down 8.11 → 7.12 → 6.79 → 6.17 → **6.07 V**, i.e. 3.03 V/cell, the hardware cutoff. The other two, `ddca697d` and `d6687c53`, remain wholly unexplained: on USB power, 34.88 and 35.39 Wh, 8.60 V, 47–52 °C, 4 GB free, load 1.5–2, and **no precursor on any sampled quantity**. The witness cannot say why they fell, but it rules out thermal, memory and power.

  **This corrects the entry below.** "11 unclean cuts" is still the right count of boots ending with no shutdown sequence, but reading it as 11 anomalies is wrong: one is an ordinary flat battery, and the eight predating the witness have no data at all — some may be the same. The absence of a shutdown sequence proves the shutdown was not orderly, not that it was mysterious.

  **The defect the flat battery exposed:** the machine ran to hardware cutoff instead of shutting down. Chain verified end to end — `CanSuspend`, `CanHibernate` and `CanHybridSleep` are all **no** on this machine (no working sleep state, and `resume=` is absent from the cmdline despite a 4 GB swapfile), while `/etc/UPower/UPower.conf` had `CriticalPowerAction=Auto` with `AllowRiskyCriticalPowerAction=false`. `Auto` tries HybridSleep, then Hibernate, then PowerOff; the first two are impossible here and the third is refused by the risky flag. **So upower did nothing at the 2 % threshold**, and every unplugged session ends at 6.07 V — risking filesystem damage and wearing the pack. Fixed: `CriticalPowerAction=PowerOff` + `AllowRiskyCriticalPowerAction=true` (backup kept as `UPower.conf.avant-criticalaction-20260903`). The flag is called risky because a forced power-off loses unsaved work — which is precisely what the hardware cutoff already did, minus the filesystem risk.

  Two more of my own leads were wrong here and are logged for the pattern: I read a D-Bus owner change as upowerd **dying**, when it marked upowerd *starting*; and I counted "3 battery warnings" that were `Clear Stale Hibernate Storage Info` lines caught by the substring "hibernat". A count of matching labels is still not a count of events.

  **`pstore-blk` is now in place — without rebuilding the kernel.** `PSTORE_BLK` and `PSTORE_ZONE` are `tristate`, so they build as modules against the existing tree: **17 seconds**, against ~28 minutes for a full rebuild, and the ABI audit had already cleared them (0 shared headers). The `setlocalversion` trap bit again — the tree calls itself `7.1.0-next-20260626-nft+` while the running kernel is `…-nft`, so the build needs an explicit `KERNELRELEASE=`; without it the vermagic mismatches and the modules will not load. A dedicated 32 MiB partition was cut from the free space at the end of the disk (`/dev/sda4`, `SP12PSTORE`) because pstore-blk writes **raw** to whatever device it is given; the partition table is backed up at `/data/sp12data/gpt-sda.avant-pstore-20260903` and every existing partition was verified intact afterwards. Two load-time traps, both worth keeping: `blkdev=PARTUUID=…` fails with `-2` — that form is only resolved during early boot, not from a runtime-loaded module, so a real path is required; and `pstore: backend 'ramoops' already in use: ignoring 'pstore_blk'` — the kernel accepts **one** pstore backend, and built-in ramoops takes the slot. Hence `pstore.backend=pstore_blk` on the kernel command line, added to the everyday GRUB entry **only**, leaving the frozen rescue entry untouched.

  ⚠️ **Do not expect this to explain the cuts.** They produce no panic — the kernel does not fall over, it stops — and `max_reason=2` only fires on Oops and Panic, so no kmsg dump will ever be written for this class of event. The value is the **console zone** (`console_size=2048`), which records kernel console output continuously and should therefore hold the last messages before a hard cut. With `best_effort=1` — the UFS driver exposes no dedicated pstore support, so writes go through the ordinary block layer — there is no guarantee the very last bytes reach the disk. **Takes effect at the next boot**, which is also the only way to find out whether the console zone survives the UEFI/slbounce chain any better than the DRAM one did.
- **2026-08-27** — **Two spontaneous reboots, no cause found — and the tool meant to record one has never worked.** The machine reset itself twice in twelve hours: 26 August 20:43:54 after 8 h 56, and 27 August 08:38:34 after 11 h 06. **A later sweep over the full journal — 136 boots back to 27 July — showed these were not isolated, and that my "four other recent boots ended cleanly" was an artefact of looking at a six-boot window.** There have been **11 unclean cuts**, and the rate is climbing steeply: **5 in the 24 days from 27 July to 20 August** (0.21/day), then **6 in the 8 days from 26 August to 3 September** (0.75/day) — a **3.6×** increase. Between them sits a clean 5-day gap, 21–25 August, with none at all, so the recent events cluster rather than spread evenly. The 20 August "freeze" documented in the entry below is one of them, not a one-off. ⚠️ Method note for anyone repeating this: a boot is classed as a cut by the *absence* of shutdown markers, so **the currently running boot always looks like a cut** — it has not shut down yet. Exclude boot 0 or you will report a twelfth event that never happened. Boot *indices* also shift with every reboot: `-1` does not name the same boot a week later. Key any cross-session analysis on the boot UUID, never the index — I re-derived a chronology from indices a week on, concluded the original dates were wrong, and had to retract that; the UUIDs showed the first dates had been right all along. Both cuts share a signature: the journal stops mid-activity with **no shutdown sequence and no error of any kind in the preceding ten minutes**, the last kernel message minutes to hours earlier and unrelated (a Bluetooth trackball reconnecting). Ruled out: the battery (100 %, 88 % health, 29.9 °C, on USB-C — no discharge), the watchdog (`qcom_wdt` present but armed by nobody — `RuntimeWatchdogUSec=0`, no process holds `/dev/watchdog`), and the GPU (zero faults; all 19 `msm`/`adreno` lines are boot-time init). **I cannot say why it fell.** Firmware or the EL2 hypervisor remains, but that is elimination, not evidence.

  What the investigation did establish is worse than the reboots. **`ramoops` has never retained anything on this machine.** `ramoops: uncorrectable error in header` appears on **every** boot — including the four that ended with a clean `systemctl reboot`, i.e. a warm reset where DRAM should survive. Checked across the **whole journal**: of 136 boots, 64 have ramoops registered and **all 64 carry the header error — not one exception**; the other 72 predate the region being configured. `/sys/fs/pstore` and `/var/lib/systemd/pstore` empty, always. The region is correctly reserved (`ramoops@a0000000`, 1 MiB, `map non-reusable`), the backend registers, the `ramoops-1` console is enabled — the kernel writes, and the content does not survive the UEFI/slbounce chain. Consistent with a Secure Launch that scrubs memory. **An empty `pstore` therefore proves nothing and must never again be cited as evidence** — corrected in `systeme/README.md`, `kernel/RECETTE-REBUILD.md`, and in the two entries below that leaned on it.

  Two of my own inferences during this same investigation were wrong and are recorded because the pattern repeats: I read "cold reset" out of the ramoops error before checking whether ramoops ever works (it does not, so the message says nothing about the reset type); and I took a `drkonqi-coredump-**processor**` line for a live `plasmashell` crash, when it was the same stale core file — identical PID, hash and timestamp — being re-processed at each session start. A processor line is not a crash event, the same way a grep on labels is not a count of events.

  Put in place instead: a **fsync'd witness** (`/usr/local/bin/sp12-temoin.js`, Node, `sp12-temoin.service`, log in `/data/sp12data/temoin/`). It samples every 30 s — max thermal zone, battery energy and voltage, AC/USB, CPU frequencies, load, free memory — and each line is `fsync`'d, so the last one before a cut is on disk. It will not say *why* the machine fell; it says what state it was in, and — through the presence or absence of a `"type":"stop"` marker written on SIGTERM — **whether the shutdown was deliberate**. That is the one thing it establishes with certainty. Prepared but **not applied**: `pstore-blk` would put real kernel dumps on the UFS disk instead of scrubbed DRAM. ABI audit passed — `CONFIG_PSTORE_BLK`, `PSTORE_ZONE`, `PSTORE_RAM`, `PSTORE_COMPRESS` touch **0 shared headers**. It writes **raw** to whatever `CONFIG_PSTORE_BLK_BLKDEV` names, so it needs a dedicated partition; 1.3 GiB is free at the end of `/dev/sda` (sectors 124634368–124966906). The boot disk's partition table is not modified without an explicit decision.

- **2026-08-20** — **The static RTC offset drifts, and the documentation said it did not.** A freeze during boot sent me looking at the journal, and the freeze itself yielded nothing — no panic, no OOM, no hung task, ~~empty `pstore`~~, the log simply stops mid-sentence at 10:53:44. **The `pstore` observation was worthless and is struck: as established on 2026-08-27, ramoops has never retained anything on this machine, so it is empty after every boot, incident or not.** The rest of the finding stands on the journal alone. The four preceding boots all ended cleanly, ~~so it is an isolated event~~ — **struck: the 2026-08-27 entry establishes it as one of 11 unclean cuts since 27 July, on a curve that is accelerating. A four-boot window was too narrow to support the word "isolated".** A hang leaving no trace at all points below Linux, at firmware or the EL2 hypervisor, and I have no evidence to go further. What the investigation *did* find is ours. Measured at the second boundary against NTP-synced time, the same method both times: **20 ms** of error just after the offset was set on 5 August, **3615 s** — 1 h 0 min 15 s — on 20 August. That is roughly **250 s/day**, i.e. the PMIC counter runs about **0.29 % slow** against real time, an order of magnitude beyond ordinary crystal drift. The comment I wrote into `patches/0008`, the DTS and `patches/README.md` claimed the offset "stays constant for as long as the PMIC keeps counting". It does not. My warning covered only the PMIC battery going flat; I never considered the counter itself being wrong. A fixed value is good for hours, not weeks. The approach survives here **only because something else fixes the clock shortly after boot** — NTP within a minute, and the `onedriver` drop-in gates on `NTPSynchronized` — but anything reading the clock in that first minute sees an error that grows by ~4 minutes a day since the last measurement. Corrected in all four places; the compiled DTB is unchanged, since only comments moved.
- **2026-08-15** — **WiFi dropping every ~40 minutes: it was our own power saving, not the network.** Reference boot: **8 disconnections in 5 h 41**, every one carrying `reason=34` — `DISASSOC_LOW_ACK`, the AP dropping the station because it stops acknowledging frames. Signal was **−46 dBm**, i.e. excellent, so this was never a range problem: a station at ideal range that stops acking is a radio going to sleep. Two suspects cleared before concluding — `sp12-wifi-watchdog` is a boot-time `oneshot`, `inactive` during the session and with 0 firings that boot; and NetworkManager only ever reacts, its log showing `disconnected -> scanning` *after* the eviction. Fix: `802-11-wireless.powersave 2` on that connection alone, persistent across reboots. Result over **93 hours**: **zero** `reason=34`, where the previous rate predicted 131. Stronger still, the signal had fallen to −63 dBm during the observation — worse conditions, no drops. The only remaining disconnections are `reason=3`, the station leaving deliberately, matching two clean shutdowns. ⚠️ The power cost could **not** be measured and should not be claimed: expected order of magnitude is 0.1–0.3 W, but readings scattered over ±1 W because a process was pinning a full core — five to ten times the signal sought. - **2026-08-11** — **Endurance test: the thermal conclusion holds, and it found a kernel oops nobody was looking for.** A 28-minute full kernel build from a clean clone, monitored every 20 s. Thermals settle the earlier doubt: peak **88 °C** for two minutes, then **22 minutes flat at 65–67 °C**, `cpu4` at its 3244 MHz maximum on 85 of 86 samples, **zero throttling** — a second, independent method agreeing with the 70-second synthetic loop. No memory pressure either: 5 MB of swap touched out of 4 GB, which is also the measured answer to whether `ZRAM` was worth having.

  What the test did surface: **the CDSP crashed unprompted, and the kernel oopsed handling it.** `fatal error received: sleep_statsi.c:537` → `rproc_trigger_recovery` → `Unable to handle kernel NULL pointer dereference`, `pc : 0x0`, `lr : rproc_start+0xc0`. Traced end to end: `rproc_trigger_recovery()` picks `rproc_boot_recovery()` because `qcom_q6v5_pas.c` never sets `RPROC_FEAT_ATTACH_ON_RECOVERY` (only `imx_rproc.c` does in this tree); that path reaches `remoteproc_core.c:1292`, `rproc->ops->start(rproc)`, called with no NULL check — and `qcom_pas_ops_no_reset`, which `qcom,broken-reset` selects, provides only `.attach`, `.da_to_va`, `.stop`, `.panic`. The recovery worker dies and the DSP stays `offline` until reboot. The ADSP was untouched, so audio kept working and the build finished; an ADSP crash would cost sound until reboot. **This is a defect in the out-of-tree attach series this repo documents as a solution**, not a regression from the rebuild. Reported to Stephan Gerhold. **Both claims in that sentence were wrong and are corrected in the 2026-08-20 entry**: the crash *is* triggerable on demand via `debugfs`, and Stephan's actual fix — `rproc->recovery_disabled = true`, not the `RPROC_FEAT_ATTACH_ON_RECOVERY` I had suggested — has since been verified on the machine.
- **2026-08-06** — **Boot 1.5 s shorter, and audio ready 3 s earlier.** `audioreach_send_cmd_sync()` gives every command a 5 s budget. `APM_CMD_GET_SPF_STATE` does not need it: it is the readiness probe `q6prm` issues before populating its children, its caller already treats failure as `-EPROBE_DEFER` and retries, and on the attach path the first probe always misses while the second always succeeds — one timeout per boot, five seconds spent waiting for a reply that never comes. Since the sound card only registers once the probe gives up, anything polling `/proc/asound/cards` blocked for the whole timeout; `sp12-audio-ucm.service` was the slowest unit of the boot at 4.4 s. `patches/0009` gives that one probe 1 s and lets the retry work: the service drops to **0.37 s**, the card appears at 5.74 s instead of 8.71 s, total boot 8.21 s → 6.74 s. Every other command keeps `5 * HZ`. The error line itself remains — the race is unchanged, only the wait is shorter. Separately, **battery**: telemetry turns out to be complete (93 % health, 34.88 of 37.45 Wh design) and charge limiting is both functional and persisted in the PMIC's SDAM, so it survives reboots and is not a per-session setting — worth knowing before setting it. Measured autonomy levers, A-B-A: 90 → 60 Hz is worth **0.9 W** (6.5 h → 7.7 h); dropping `clk_ignore_unused` / `pd_ignore_unused` is worth 0.10 W, i.e. nothing measurable, so they stay. At 4.5 W idle the session dominates the kernel — a running Electron app costs more than every tunable examined here.
- **2026-08-06** — **There is no CPU thermal throttling, and that is the correct behaviour — do not "fix" it.** The observation is real: 43 thermal zones read genuine temperatures, four cooling devices are registered (`cpufreq-cpu0` 0/11, `cpufreq-cpu4` 0/12, `devfreq-3d00000.gpu` 0/8, `ath12k_thermal` 0/100), and yet every `cpu*-thermal` and `cpuss*-thermal` zone carries a single `critical` trip at 115 °C with **zero** cooling devices bound. The CPU cooling devices exist and are wired to nothing; only `gpuss-*` has a `passive` trip (95 °C) and throttles the GPU.

  The tempting conclusion — that our vendor DTB is missing `cooling-maps` — is wrong on both counts. **Upstream does the same**: `hamoa.dtsi`, the real SoC base for the whole x1e/x1p family, defines its 24 CPU zones with a `critical` trip and nothing else. And a load test says why. Eight cores pinned:

  | | |
  |---|---|
  | idle | 35 °C |
  | +10 s | 82 °C |
  | +30 s → +60 s | 86, 86, 87, **86 °C** — flat |
  | `cpu4` frequency throughout | **3244 MHz**, the maximum, never dipping |

  That is thermal equilibrium 28 °C below the critical trip, at full clock. Adding a `passive` trip and `cooling-maps` would mean inventing a throttle temperature nobody has validated, in order to slow down a CPU that currently runs flat out and stays cool enough. It would cost performance and buy nothing.

  ⚠️ Caveat: 70 s is not a soak test. A long compile in a warm room may behave differently; worth re-measuring during a real kernel build rather than a synthetic loop.

  ⚠️ Counting trap worth recording: `ls $zone/cdev*` counts `cdev0`, `cdev0_trip_point` and `cdev0_weight` as three bindings when there is one. Count only `cdev[0-9]*$` — miscounting it is what first suggested, wrongly, that CPU throttling was already wired.

- **2026-08-05** — **Hardware clock working at EL2, and the reason EL2 costs the EFI variables.** The mechanism was measured, not assumed: after Secure Launch TrustZone still answers a version query (`TZ_OWNER_SIP` / `INFO_VERSION` → `0x1402000`) but refuses the trustlet manager (`TZ_OWNER_QSEE_OS` / `APP_LOOKUP` → `-22`). So `qcom_qseecom_uefisecapp` never probes, `efivars` never registers — 0 variables at EL2 against 110 at EL1 on the same kernel — and `qcomtee` reports `QTEE version 0.0.0` instead of `5.2.0`. Mainline cannot reload a trustlet, so this is a dead end rather than an unexplored lead. A separate experiment settled a competing hypothesis: restoring a *restricted* cache sweep over `EfiRuntimeServices{Code,Data}` in `sl_ExitBootServices()` boots fine but does **not** bring the variables back, so removing the sweep was never the cause. Knock-on effect on the clock: `pm8xxx_rtc_probe_offset()` reads its epoch offset from the UEFI variable `RTCInfo` and returns `-EPROBE_DEFER` with no give-up path while `CONFIG_EFI=y`, so the RTC never registered at all. Fixed with `qcom,rtc-offset`, a third source tried after nvmem and before UEFI (`patches/0008`); the clock is now set at 3.0 s of uptime, sixty seconds before NTP. The nvmem route used by `sc8280xp-crd`/`-arcata`/`-blackrock` (cell `rtc_offset@bc`) is not transposable: on the pmk8550 a SDAM's usable window is `0x40..0x7f`, so `0xbc` is not addressable, and SDAM 6 is densely written by firmware — not somewhere to gamble on an inference. Two traps on the way: `hwclock --show --utc` prints **local** time with its offset (`--utc` describes the RTC, not the output), and `scripts/setlocalversion` no longer honours `.scmversion`, so a module built from a git tree gets a `+` in its `vermagic` and silently refuses to load without `MODVERSIONS` — build with `KERNELRELEASE=` set explicitly.

- **2026-07-31** — **Audio working at EL2.** ADSP and CDSP are started by qebspil from UEFI before `ExitBootServices`, then *attached* by the kernel instead of started: `qcom,broken-reset` on both remoteproc nodes selects `qcom_pas_ops_no_reset` (no `.start`/`.load`), so the PAS SMC that returns `-22` is never called, and the already-running state is detected by reading the SMP2P IRQ *levels* — the DSPs signalled their boot long before Linux existed, so waiting for an edge could never work. 14 out-of-tree patches; see `patches/audio-el2-serie.md`, including the module-ABI hazard the series introduces.
- **2026-07-30** — **Internal Wi-Fi fixed at EL2.** No MSI was ever delivered — every `ITS-PCI-MSI` counter stayed at zero, PCIe root-port PME included. The cause was in our own DTS: the PCIe SMMUv3 (`iommu@15400000`) was left at `status = "reserved"`. Setting it to `"okay"` fixes it. The SMMU had been "ruled out" days earlier by a test with `arm-smmu.force_stage=1` — a parameter belonging to the SMMUv1/v2 driver, which never touches the SMMUv3. A false negative that cost days.
- **2026-07-14** — Re-established the HW-codec firmware after a restore had dropped it; a hot module reload (`modprobe -r qcom_iris && modprobe qcom_iris`) brings `/dev/video0` + `/dev/video1` back with no reboot. Documented a **safe full `pacman -Syu`** on this device: pin the entire Mesa/Vulkan userspace to a single version (`mesa`, `vulkan-freedreno`, `vulkan-mesa-implicit-layers`) so a partial upgrade can't skew the Adreno/turnip stack, with kernel + systemd held in `IgnorePkg`; cold boot validated. Added an `fstab` recipe to auto-mount the shared data partition with `nofail` + `x-systemd.automount` (see README → Stability notes).
